The Guacamayo Loop

Five nodes, one cycle. Every session generates telemetry; hooks enforce guardrails and record events; the metacognition skills derive patterns and propose changes; the retro graduates hypotheses into permanent config; improved config shapes the next session.

System Design

Three planes, one cycle. Plane 1 is where work happens — triage shapes an issue until it passes Definition of Ready, execute implements it, review measures it against Definition of Done. Plane 2 observes: the state board and identity lifecycle both write records, telemetry appends them, insights derive patterns, and a verification gate stands between a dashboard number and a retro hypothesis. Plane 3 is what retro actually changes — the four levers of the Claude setup, which shape every session on the planes above. Every box is a skill or module that actually fires; colour tracks which plane a record came from.

Plane 1 — triage → execute → review; triage and review each emit a record
Plane 2 — identity + board feed telemetry → insights → gate → retro
Plane 3 — the four levers a retro can pull

The state board sits in metacognition because it is a record, not a stage of work — triage writes to it via board.py, and /meta-wake and /meta-retro open and close issues directly. Dashed elements are stages that exist but are not automated — see Loop Health.
