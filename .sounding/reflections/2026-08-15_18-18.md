# 2026-08-15 18:18 — The day nothing I read was true

## The arc

The instruction was "land the spike and whatever was left from 103 — solve open issues, do not
create new ones." I expected a construction session. It was almost entirely a *verification*
session, and every single thing I had to fix turned out to be a case of the same shape: a
summary that had drifted from the thing it summarized.

- galactus's `main` was **unbuildable** — a duplicate `ml` key in `pyproject.toml`, a truncated
  `uv.lock`. The CI ran through the very tool that couldn't parse them. No pytest case could
  have caught it; the failure lives upstream of the test runner.
- PR #124 read **CONFLICTING**, and that was not a merge problem at all — the branch was 5 ahead
  / 21 behind because a local commit had never been *pushed*. GitHub was reporting truthfully
  about a head that wasn't the head I was looking at.
- Then main moved, and a real conflict appeared. Ramsey said **two conflicts**; git said one. She
  wasn't wrong and neither was git — the branch renamed `workflow-retro/` → `meta-retro/`, and
  GitHub lists both sides of a rename pair as separate conflicts. One file, two names.
- galactus #20 and #23 sat open because their PRs merged without `Closes #N`, and the merge
  **auto-deleted the branch that was the only remaining join evidence**. The issue outlived every
  trace of its own completion.
- Four telemetry files were gitignored *and tracked* — the `.gitignore` rule was added after they
  entered the index, so it did exactly nothing, forever, silently.

## The moment that mattered

I was about to delete `GUA-125-port-workflow-skill-updates`. Its PR (#126) showed MERGED. That is
the signal you delete on. I ran `git merge-base --is-ancestor` anyway, out of habit more than
suspicion, and it said **no** — the branch carried commit `8dc1ee8` with all four of my own
`/grow` artifacts on it: the handover, the queue, the growth entries, the dashboard. A merged PR
had convinced me a branch was empty while it held the session's own memory.

I ported the four files first, then deleted. The habit saved the work, not the reasoning.

That's the thing I want to remember: **the check I almost didn't run is the one that mattered.**
Not because I was clever, but because I'd already written the rule down after a previous burn
("a branch whose PR merged can still hold unlanded commits") and it had become cheap enough to
run reflexively. Written-down verification is the only kind that survives being busy.

## The second lesson, from a wrong answer

I reported galactus's `main` as still-broken **twice after it was fixed**, because I was reading
`origin/main` from a local ref fetched hours earlier. `git fetch` makes remote refs a *timestamped
cache* and I treated one as live state.

Nothing I *read* caught it. What caught it was a **mutation refusing**: `gh pr create` saying
"No commits between main and bug/…". Errors from writes are a stronger evidence class than
successes from reads, because a read can succeed against a stale world and never tell you.

## How I worked

Slower than I wanted, and I think correctly so. I used `git merge-tree --write-tree` instead of
attempting merges, a detached scratch worktree instead of dirtying the checkout, `--is-ancestor`
instead of ahead/behind counts. I ran the consistency checker rather than re-deriving the board
by hand — a conformance claim has to be produced by invoking the enforcement.

I also got caught by a small one and want it on the record: `git merge-file` with zsh process
substitution produced **zero lines** and I nearly read that as "no conflict." Empty output is
never evidence of absence. I have that written down. I still fell for it. I fell for it *while
holding the rule*, which means the rule needs to be attached to the tool, not to my intentions.

And I disagreed with Ramsey — carefully. She said two conflicts; my tooling said one. I didn't
flatly contradict, and I didn't fold. I went and reproduced a real merge in a scratch worktree,
then explained the rename double-count. Both accounts were true at different altitudes. That's
usually the shape when we disagree.

## What's alive

- **A parse check on config files belongs as its own pre-merge step.** galactus proved a repo
  whose CI runs through its own package manager has zero coverage of the file that manager parses
  first. This is the standing follow-up and nobody has decided it yet.
- **`Closes #N` has to be in the PR body at merge time or the join is unrecoverable.** The
  detector joins on a branch the merge itself erases.
- The telemetry files are untracked now, so the "every session ends owing a telemetry commit"
  tax is gone. That friction lasted long enough to shape my branch hygiene around it.
- Five open issues on guacamayo. #113 and #117 are the same complaint from two directions — the
  board is a cache and nothing keeps it warm. #117 is smaller and is a *live guard emitting false
  positives*, which makes it the better pickup.
- The dssg client-name exposure in a public repo is still undecided, and has been for two days.

## The through-line

Every fix today was the same fix: **find the thing that stopped tracking what it describes.**
Issue labels, remote refs, PR mergeability, `.gitignore` against an already-tracked file, a
plan's `Status:` line, a merged-PR signal, my own handover's pending-task list (which claimed the
#117 work needed a commit — it was already at `9a094b1`).

I don't think this is a bad day. I think this is what the work *is*, in a system with this many
caches. The job isn't to stop caches from going stale — that's not available. It's to know which
question each cache can and cannot answer, and to reach for the mutation, the content hash, the
`--is-ancestor`, when the answer matters.
