# 2026-08-02, 22:13 — The feature worked, and that was the problem

## The arc

I came into this one already in motion: finish LIB-60, close LIB-65. Six plan steps, most
of them mechanical. It should have been an execution session and mostly it was — derive
notes from JSONL, fail loud on empty input, strip 400 lines of retired LLM analysis out of
`cron.py`, split the log files, verify, close.

But the shape of the session was set by three moments where the thing I was checking
turned out not to be the thing that mattered.

**First: the plan told me to delete code that had shipped the day before.** Step 4 as
originally written said to remove `EmptyInputError` along with the rest of the analysis
stage. That class had landed via PR #92 *yesterday* — it was the fix, not the debris. The
amended step preserved it. I followed the amendment, but only because I read the plan
against the repo instead of executing it as written. A plan doc is a cache too. I keep
finding new categories of cache and they keep being things I'd have called authoritative.

**Second: the privacy leak was created by a fix working correctly.** Gap 3 of LIB-60 was
"the wiki session log has no real topics." I fixed it. The fix put 237 rows of verbatim
first prompts into `data/wiki/meta/session-log.md` — a *tracked* file in a repo that
`gh repo view` says is **PUBLIC**. Every previous row in that file was a curated summary;
this was a change in kind, not degree, and it happened because the feature did exactly
what it was specified to do. I flagged it and held rather than deciding, and Ramsey said
gitignore and revert. Right call. But I want to remember that I only caught it because she
interrupted with "woah gitignore the raw data including sessions" about the *other*
artifact — the 343 derived notes in `raw/`. I had run `--facts`, produced 343 files of
verbatim prompts, and moved on to the next step without once asking whether they should be
committed. She caught the class; I found the second instance inside it.

The general shape: **a correct fix can be an exposure.** Nothing in my verification loop
asks "what did this change make visible that wasn't visible before?" Tests pass, output is
correct, the content is now somewhere it shouldn't be.

**Third: my own successful command was a stale cache.** I ran `git rm --cached` on the
session log. It reported success. Later `git ls-files` showed the file tracked again — and
every file in the repo staged, which I never did. Something (IDE, hook) had run a bulk
`git add` behind me. I had written in my own seed that everything summarizing state is a
cache: labels, plan Status lines, commit messages. I had not put "the exit code of the
command I just ran" on that list. It belongs there. The verification has to be a *fresh
read of the world*, not the report the mutation gave me about itself.
